cli-harness v0.1.0 / architecture

From an installed binary to a tested agent harness

Two views of the same skill. First the order of work when someone runs /cli-harness <binary>. Then the files: what lives in the repo, what gets generated, and which script touches what.

1. The flow

Phases 0 to 6 of SOP.md. Two refusal exits at the top. One feedback loop at the bottom: if the done gate fails, go back to Build.

2. The components

Left: the skill directory in the repo. Right: what one run leaves behind in ./harness-<binary>/, plus the real binary it calls. An arrow that ends on a folder edge means the script reads the whole folder.

Where it refuses

probe.py exits 2 when the binary is not on PATH and exits 3 when it is on the denylist (rm, dd, sudo, git, curl, ssh and others). A denylisted binary is never executed, and nothing is ever installed.

SOP.md adds one more refusal that code cannot enforce: skip any binary that moves money, deletes user data or touches credentials, even if it is not on the list.

  1. harness_json

What stays fixed

  • Scripts use the Python standard library only. The wrapper needs click.
  • At most 6 commands in v1.
  • Mutating commands take --dry-run.
  • No raw passthrough command.
  • Done means 9/9 and pytest green. Nothing else counts.
